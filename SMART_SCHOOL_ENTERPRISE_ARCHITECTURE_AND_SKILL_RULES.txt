SECTION 1: CORE ARCHITECTURAL PHILOSOPHY & DESIGN DIRECTIVES
--------------------------------------------------------------------------------

1.1 THE SYNCHRONOUS-TO-ASYNCHRONOUS BRIDGE
- Client applications (Web browsers, mobile devices, IoT turnstiles, biometric gates)
  require deterministic, rapid responses (< 100ms for web, < 15ms for IoT hardware).
- Traditional systems couple the web request with third-party telco SMS gateways,
  heavy analytics calculations, and distributed database writes. Under peak traffic
  (07:00 AM - 07:45 AM morning gate rush), this causes thread pool exhaustion and
  HTTP 504 Gateway Timeouts.
- Architectural Mandate: The API Gateway and Ingress Controllers accept high-throughput
  commands, validate schemas and authentication, persist to a local Transactional
  Outbox, publish an immutable event to Apache Kafka, and IMMEDIATELY return
  "HTTP 202 Accepted" containing a tracking ID.
- Downstream workers consume the Kafka log asynchronously to perform SMS dispatch,
  parent mobile push notifications, GPA re-calculations, and ledger balancing.

1.2 MULTI-BRANCH TENANT ISOLATION
- The architecture is inherently hierarchical:
    Organization / District -> School Tenant -> Physical Campus / Branch.
- Every incoming HTTP request MUST supply the target branch context either through
  a verified JWT claim or an "X-Branch-ID" header.
- PostgreSQL Row-Level Security (RLS) guarantees at the database engine level that
  staff at Branch A cannot read or modify student records from Branch B.

1.3 VIRTUAL THREADS (PROJECT LOOM)
- The Spring Boot engine MUST run on Java 21+ with "spring.threads.virtual.enabled=true".
- Every Tomcat HTTP connection executes on a lightweight virtual thread, enabling
  tens of thousands of concurrent I/O requests with minimal memory footprint.

SECTION 2: AGENT SKILL RULES & CODING STANDARDS ("VIBE CODE READY")
--------------------------------------------------------------------------------

When any AI coding assistant or engineer generates or modifies code for this
codebase, the following immutable directives MUST be followed:

[RULE 01] ZERO RAW CONTROLLER QUERIES:
- Controllers must ONLY validate inputs, extract security headers, and delegate to
  Command or Query service layers. No JPA logic in Controllers.

[RULE 02] MANDATORY KAFKA EVENT ENVELOPE:
- Every event published to Kafka MUST wrap its payload in the standardized
  "EventEnvelope<T>" containing eventId, eventType, tenantId, branchId,
  correlationId, and timestamp. Never publish raw, un-enveloped JSON payloads.

[RULE 03] STRICT PARTITION KEY STRATEGY:
- Never publish Kafka messages with null keys. Always use natural domain keys:
    Attendance Events : "{branchId}#{studentId}"
    Academic Grading  : "{branchId}#{courseId}#{studentId}"
    Finance / Billing : "{tenantId}#{studentId}"
  This ensures strict chronological event ordering at the partition level.

[RULE 04] ZERO DIRECT DUAL-WRITES:
- When an operation requires both a database update and a Kafka event publication,
  use the Transactional Outbox pattern or write to Kafka with "acks=all" and
  "enable.idempotence=true". Never assume an HTTP write and Kafka send succeed
  together without transactional encapsulation.

[RULE 05] TYPE SAFETY & CONSTANT TOKENS:
- Never use magic strings for user roles, attendance states, or event types.
  Always use Java Enums or strongly typed constant interfaces.

[RULE 06] CLEAN CONTEXT CLEANUP:
- Any ThreadLocal storage (such as TenantBranchContext) MUST be cleared in a
  "finally" block within filters or interceptors to prevent memory leaks and
  cross-tenant pollution across thread pools.

[RULE 07] RESILIENCE & DEAD-LETTER QUEUES (DLQ):
- All Kafka consumers must configure error handlers with exponential backoff.
  Poison-pill messages that fail after 3 retries must be routed to a ".dlq" topic
  and never crash the consumer loop.

SECTION 3: COMPLETE INSTITUTIONAL ROLES & ACCESS CONTROL MATRIX (RBAC / ABAC)
--------------------------------------------------------------------------------

The platform defines 6 administrative and academic staff roles, plus 2 consumer roles:

1. SUPER_ADMIN (Platform Governor)
   - Scope: Universal (Cross-tenant, Cross-branch).
   - Bypasses PostgreSQL Row-Level Security via session flag "app.bypass_rls = true".
   - Permissions: Provision new schools, create branches, assign Deans, audit system logs,
     configure global billing policies, view cross-campus analytics.

2. ADMIN (Campus Dean / Principal)
   - Scope: Assigned Branch Only.
   - Permissions: Manage campus teachers, librarians, receptionists, accountants;
     approve student leave requests; view campus-wide attendance and academic standing;
     broadcast campus-wide emergency notifications.

3. ACCOUNTANT (Finance Officer)
   - Scope: Assigned Branch Only.
   - Permissions: Configure tuition fee masters, generate batch student invoices,
     record manual cash/bank payments, view due fees, issue receipts, reconcile
     online payment gateway transactions, manage expense categories.
   - Prohibited: Modifying student grades, taking attendance, or editing curriculum.

4. RECEPTIONIST (Front Desk Officer)
   - Scope: Assigned Branch Only.
   - Permissions: Manage visitor logs, phone call records, postal dispatch/receive,
     admission inquiries, issue visitor badges and gate security passes.
   - Prohibited: Financial transactions, grading, and curriculum modification.

5. TEACHER (Academic Instructor)
   - Scope: Assigned Classes and Assigned Branch Only.
   - Permissions: Take classroom attendance (roll call), submit assignment scores,
     enter midterm/final exam marks, view class rosters, issue behavioral incidents.
   - Prohibited: Accessing tuition fee ledgers or issuing books in the library.

6. LIBRARIAN (Media & Resource Officer)
   - Scope: Assigned Branch Only.
   - Permissions: Manage book catalog, index ISBNs, record book issues and returns,
     track student library cards, compute and record overdue library fines.
   - Prohibited: Modifying grades or accessing institutional accounting.

7. PARENT (Guardian / Consumer)
   - Scope: Own Children Only.
   - Permissions: View real-time check-in/out attendance timeline, view published
     report cards, pay pending tuition invoices via mobile app, receive SMS alerts.

8. STUDENT (Learner / Consumer)
   - Scope: Own Identity Only.
   - Permissions: View timetable, class schedule, homework assignments, library
     borrowing history, and digital student ID badge.

6.1 CANONICAL EVENT CONTRACT (JSON SCHEMA)
All topics in this platform adhere strictly to this envelope:

{
  "metadata": {
    "eventId": "UUID (v4)",
    "eventType": "String (e.g., 'school.attendance.student.scanned')",
    "aggregateType": "String (e.g., 'STUDENT_ATTENDANCE')",
    "aggregateId": "String (e.g., 'att_88921')",
    "tenantId": "String (e.g., 'ten_ideai_hq')",
    "branchId": "String (e.g., 'brn_phnom_penh')",
    "timestamp": 1789123456789,
    "correlationId": "String (traceparent or request ID)",
    "version": "1.0.0"
  },
  "payload": {
    /* Strongly-typed domain data */
  }
}

+----------------------------------+------------+-----------------------+---------------------+
| school.attendance.raw-scans      | 12         | {branchId}#{studentId}| Attendance Service  |

+----------------------------------+------------+-----------------------+---------------------+

6.3 KAFKA PRODUCER CONFIGURATION DIRECTIVES:
- acks=all (Requires acknowledgment from all in-sync replicas)
- enable.idempotence=true (Guarantees no duplicate writes on network retry)
- retries=2147483647 (Infinite retries until delivery or timeout)
- max.in.flight.requests.per.connection=5
- compression.type=zstd (Highest compression ratio under JSON payloads)
- linger.ms=20 (Batches high-volume morning scans efficiently)

SECTION 7: NEON SERVERLESS POSTGRESQL & ROW-LEVEL SECURITY (RLS)
--------------------------------------------------------------------------------

7.1 WHY NEON SERVERLESS POSTGRESQL?
- Zero local Docker / RAM footprint on your computer.
- Automatic autoscaling and branching for zero-risk schema migrations.
- Native TLS/SSL encryption enforced via "sslmode=require".

7.2 SPRING BOOT APPLICATION.YML TUNING FOR NEON:
HikariCP must be configured to support Neon's serverless suspend/resume cycle:

spring:
  datasource:
    url: ${NEON_DATABASE_URL} # jdbc:postgresql://ep-...neon.tech/neondb?sslmode=require
    username: ${NEON_DATABASE_USER}
    password: ${NEON_DATABASE_PASSWORD}
    driver-class-name: org.postgresql.Driver
    hikari:
      maximum-pool-size: 10
      minimum-idle: 2
      idle-timeout: 300000        # 5 minutes
      max-lifetime: 600000        # 10 minutes
      connection-timeout: 30000   # 30 seconds
      connection-test-query: SELECT 1

7.3 NATIVE ROW-LEVEL SECURITY (RLS) POLICIES IN POSTGRESQL:

-- Enable RLS on core student and operational tables:
ALTER TABLE students ENABLE ROW LEVEL SECURITY;
ALTER TABLE attendance_records ENABLE ROW LEVEL SECURITY;

-- Create Tenant Branch Isolation Policy:
CREATE POLICY branch_isolation_students ON students
    FOR ALL
    TO PUBLIC
    USING (
        current_setting('app.bypass_rls', true) = 'true'
        OR branch_id = current_setting('app.current_branch_id', true)
    );

CREATE POLICY branch_isolation_attendance ON attendance_records
    FOR ALL
    TO PUBLIC
    USING (
        current_setting('app.bypass_rls', true) = 'true'
        OR branch_id = current_setting('app.current_branch_id', true)
    );

7.4 AUTOMATIC SESSION VARIABLE INJECTION:
In Spring Boot, an Aspect runs before every repository method:
entityManager.createNativeQuery("SELECT set_config('app.current_branch_id', :bId, true)")
             .setParameter("bId", TenantBranchContext.getBranchId())
             .getSingleResult();

SECTION 10: DISTRIBUTED RELIABILITY: OUTBOX PATTERN, SAGA & DLQ

10.1 THE TRANSACTIONAL OUTBOX PATTERN
To eliminate distributed dual-write inconsistency (where database write succeeds
but Kafka publication fails):
1. In a single ACID PostgreSQL transaction:
   a) Insert student attendance record into "attendance_records".
   b) Insert canonical event into "transactional_outbox" with "is_published = FALSE".
2. A lightweight background worker or Debezium CDC reads the outbox table and streams
   the records to Kafka.
3. Once Kafka responds with an ACK, set "is_published = TRUE".

10.2 THE SAGA PATTERN FOR TUITION PAYMENTS
Tuition payment involves 3 distinct microservices:
1. Payment Service: Confirms bank transaction.
2. Academic SIS: Updates student active registration status.
3. Ledger Service: Balances invoice account to $0.

Workflow (Choreographed Saga):
- Step 1: Payment Service publishes "finance.payment.completed".
- Step 2: Ledger Service listens, credits account, and publishes "ledger.invoice.settled".
- Step 3: If Ledger fails, it publishes "ledger.settlement.failed".
- Step 4: Payment Service consumes the failure event and triggers a compensating
  refund or marks invoice as "DISPUTED".

10.3 DEAD LETTER QUEUE (DLQ) CONFIGURATION
- When a Kafka consumer encounters a malformed payload or unrecoverable database
  constraint failure:
  - Retry 3 times with 1-second fixed backoff.
  - On 4th failure, forward the raw record to:
    "school.attendance.raw-scans.dlq" with exception stack trace in the record header.
  - Consumer commits offset and moves to the next message. No cluster blockage.
